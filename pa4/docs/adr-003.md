# ADR-003 — Canonical Order Translation and Enrichment

**Status:** Accepted  
**Date:** 2026-10-11

## Context

The web, mobile, and B2B sources describe the same logical order but use different field names and representations. Web orders use ISO dates and product IDs such as `PROD-001`; mobile orders use compact field names, numeric currency and status codes, Unix timestamps in seconds, and numeric product IDs such as `001`; B2B orders use XML, SKU-prefixed product IDs, and currency attributes. The B2B XML is encoded in Windows-1257, so decoding it as UTF-8 can corrupt Latvian characters. The XML parser also represents attributes with an `@_` prefix and may return a single `LineItem` as an object or multiple items as an array.

Product prices must come from the pricing API, which can return an unknown-product response or fail. Payment details in source records must not be copied into the canonical order. The canonical schema is provided by the assignment and is not owned by this implementation.

## Decision

I implemented separate `translateWeb`, `translateMobile`, and `translateB2B` functions in `transform.ts`. Each maps its source fields explicitly into the canonical model instead of copying the source object. This prevents unrelated fields, including payment details, from leaking into the output.

`normalizeProductId` applies the source-specific product ID rules. `epochSecondsToIso`, `mapCurrencyCode`, `mapMobileStatus`, and `mapB2BStatus` convert source-specific representations. `decodeB2BXmlBytes` decodes XML using Windows-1257, and the existing `fast-xml-parser` dependency parses the XML. The B2B translator handles both single-object and array forms of `LineItem` and ignores decorative fields such as `UnitListPrice`.

`enrichFromPricing` requests each product's current price using the configured API key. `toDecimalAmount` uses `toFixed(2)`, so a price of `4.5` becomes `"4.50"`. Prices remain decimal strings because that is the canonical schema's required representation. A 404 produces an `UNKNOWN_PRODUCT` warning; other unsuccessful responses or request failures produce a `PRICING_API_ERROR` warning. `enrichItems` omits an item that could not be enriched while retaining the warning. If no items remain, the translator returns a null order with its warnings rather than inventing prices or returning an empty order.

Each translator constructs the output using only explicitly selected canonical fields. Payment-related fields are deliberately omitted from web, mobile, and B2B output. The supplied canonical schema and fixtures remain unchanged.

## Alternatives considered

- **Fail the entire order when one item cannot be priced:** rejected because it would discard valid items when only one product fails enrichment. The chosen approach preserves successfully enriched items and explains omissions through warnings.
- **Store prices as integer cents:** rejected because the required canonical schema represents `unitPrice` as a two-decimal string. Using the specified representation avoids a schema mismatch.
- **Cache pricing responses:** rejected for this assignment because caching could hide catalog price changes. Requests are made to the API so current prices are used.
- **Write a custom XML parser:** rejected because `fast-xml-parser` is already available and handles the XML structure. Explicitly normalizing its single-item and multi-item results is simpler to maintain.

## Consequences

The three sources now produce equivalent canonical orders apart from source-specific identity fields, and current pricing is not hardcoded. Explicit field mapping reduces the risk of leaking sensitive data or accidentally accepting unrelated source fields. Warnings make partial enrichment failures visible without unnecessarily discarding all valid items.

The implementation still depends on the external schema and pricing API contract. If the canonical schema adds a required field, the translators and tests will need updating. A new source may require another normalization branch, and unknown currency or status codes currently fall back to the existing helper behavior rather than providing strict validation. Calling the pricing API for every item also adds latency and makes enrichment dependent on service availability. Before this model outlives the course, I would add explicit schema validation at the integration boundary, stronger handling for unsupported codes, contract tests, and documented versioning for the canonical model.

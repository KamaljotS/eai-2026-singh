**Status:** Accepted

## Context

The order-processing system sends each accepted order to payment, inventory, and notification services independently through RabbitMQ. Messages may be delivered again, consumers may fail temporarily, and invalid messages should not be retried indefinitely. The system therefore needs consistent correlation tracing, bounded retries, a way to isolate permanently invalid messages, and protection against duplicate notifications.

Three decisions were especially important. First, correlation IDs must be available to every consumer without modifying the canonical order payload. Second, transient failures need a bounded retry path that returns a message only to the consumer that failed. Third, notification processing must remember previously processed orders across service restarts.

## Decision

The order service validates incoming requests against the canonical order JSON schema before publishing. For each accepted order, it generates a UUID v4 correlation ID and places it in the AMQP `headers.correlationId` header, leaving the canonical order body unchanged. The order is published persistently to the durable fanout exchange `orders.exchange`. The order service also stores the order in memory so it can be retrieved by correlation ID while that service instance remains running.

Each consumer handles its own queue independently. Transient failures use a dead-letter retry topology: a failed message is routed to that consumer's retry queue, waits for the configured 1-second TTL, and returns through `orders.return.exchange` to the original consumer queue. The retry count is limited to three attempts; messages that exhaust the retry limit go to `orders.dlq`. Retry history is used to determine the count. Malformed JSON and permanent validation failures are sent to `orders.invalid.exchange` with their original message bytes and headers, then acknowledged instead of retried.

The order service's `POST /dlq/replay` endpoint retrieves messages individually from `orders.dlq`, removes RabbitMQ retry-history headers, preserves the remaining message headers and content, and publishes each message to `orders.return.exchange` using its `originQueue` header as the routing key. It acknowledges a message only after publishing it.

Notification idempotency is persisted in `/data/processed-ids.json`. The notification service checks the correlation ID before recording a notification. For a new ID, it appends one JSON line to `/data/notification.log`, records the ID in the processed-ID file, publishes a notification result, and acknowledges the message. A duplicate ID is acknowledged without appending another notification line.

## Alternatives considered

- **AMQP's native `properties.correlationId`:** This would use a standard AMQP property, but the assignment's message contract specifies a correlation ID in the headers. The implementation follows that contract and keeps correlation metadata out of the canonical payload. Any future producer or consumer must preserve this header consistently.
- **An in-memory notification ID set:** This is simpler, but restarting the notification service would erase its deduplication history. A redelivered order could then append a second notification log entry. Persisting IDs in a file preserves that history across restarts.
- **Immediate requeue with `requeue=true`:** This avoids a separate retry topology, but can cause a failing message to cycle rapidly without a delay or clear retry limit. The TTL-based retry queues provide a one-second delay and a bounded path to the DLQ.
- **Fan-out retry routing:** Returning a failed message to a fanout exchange would send it to multiple consumers, including services that had already processed it successfully. Direct routing through `orders.return.exchange` sends it only to the original consumer queue.
- **More retries or a longer delay:** These might help a slow downstream service recover, but would delay final failure handling. The implementation retains the scaffold's three-attempt limit and one-second retry TTL.

## Consequences

The system provides independent consumer processing, correlation tracing, bounded retries, an invalid-message path, and a DLQ that can be replayed deliberately. Persistent notification IDs reduce duplicate log entries when messages are redelivered after a restart.

These choices also have limits. If a producer or future consumer drops `headers.correlationId`, end-to-end tracing and notification deduplication may fail. The order service's in-memory order lookup does not survive a restart. File-based notification state is not a distributed coordination mechanism: running multiple notification-service replicas with separate or concurrently modified files can cause inconsistent deduplication, and writing the log and ID file is not one atomic transaction.

A three-attempt retry policy may also be too short for a downstream service that remains unavailable. Such an order can end up in the DLQ rather than complete automatically, so operators must inspect and replay failed messages after addressing the cause. Replay does not guarantee success; a persistently failing consumer can send the message back to the DLQ. These operational costs are accepted in exchange for bounded retries and isolation between consumers.

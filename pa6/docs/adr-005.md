# ADR-005 — Sequential Checkout Saga with Compensation and Idempotency

**Status:** accepted  
**Date:** 2026-10-29

## Context

For PA6, I had to build a checkout orchestrator that communicates with four services: payment, inventory, shipping, and notification. The challenge was that each service could fail or time out after an earlier step had already succeeded.

For example, if payment is authorized and inventory is reserved but shipping fails, the order cannot simply be marked as completed. The orchestrator needs to undo the earlier operations where possible.

Payment supports refunds and inventory supports releasing reservations. However, shipping and notification do not provide cancellation endpoints. This means the saga cannot always reverse every external action.

I also needed to handle repeated checkout requests safely. Without idempotency, retrying a request could authorize another payment or reserve inventory again.

## Decision

I decided to use a sequential saga. The orchestrator calls the services in this order:

1. Authorize payment.
2. Reserve inventory.
3. Create shipping.
4. Send notification.

I implemented this in `orchestrator/src/server.ts`. The `callStep()` function sends HTTP requests to the services, handles their responses, and records each operation in the execution trace.

If a step fails, the orchestrator stops processing the remaining steps. It then compensates for successful earlier operations in reverse order. If inventory was reserved, it is released first. If payment was authorized, it is refunded afterward.

The orchestrator distinguishes timeouts from normal service failures. Axios timeout errors are mapped to HTTP 504, while business failures generally return HTTP 422. If compensation fails, the response uses the code `compensation_failed`.

For idempotency, I used the `Idempotency-Key` header and a SHA-256 hash of the original request body. If the same request is repeated after completion, the orchestrator returns the stored response without calling the services again. If the same key is used with different request data, it returns HTTP 409. A request using a key that is already being processed also receives HTTP 409.

I store the idempotency records and saga results in JSON files under `/data`, allowing completed results to survive an orchestrator restart.

I defined the OpenAPI contract before implementing the saga. This helped me specify the request structure, HTTP responses, and trace fields early. During testing, I discovered that the public test scenarios used a simplified order structure instead of the canonical order format. I added a compatibility function to handle those scenarios while retaining validation for canonical orders.

## Alternatives considered

One alternative was to call all four services in parallel. This could reduce processing time, but it would make compensation more difficult because several operations could succeed or fail at nearly the same time. I chose sequential execution because it provides a predictable order and makes rollback easier to manage.

Another option was to add cancellation endpoints for shipping and notification. That would make compensation more complete, but the assignment treats those services as external systems that the orchestrator does not control. I therefore kept compensation limited to the available inventory release and payment refund operations.

I also considered using a database instead of JSON files for persistence. A database would be more reliable for concurrent requests, but JSON files were simpler to implement and sufficient for demonstrating the required persistence behavior in this assignment.

## Consequences

The main advantage of this design is that the checkout process is easier to follow and debug. Each service call is recorded in the trace, including failed operations and compensation steps. The public tests also helped verify the behavior for payment failures, inventory failures, shipping timeouts, and repeated requests.

There are some disadvantages. Because the calls are sequential, checkout takes longer than it would with parallel processing. Shipping and notification cannot be undone, so compensation does not guarantee a complete rollback of every external effect.

If a fifth service were added, I would need to update the execution sequence, determine whether it supports compensation, and extend the relevant tests and API documentation.

The current JSON storage also has limitations. Two requests using different idempotency keys but the same order ID could run independently. Concurrent writes or a process crash between persistence operations could also cause inconsistencies. For a production system, I would use a transactional database and stronger concurrency controls.

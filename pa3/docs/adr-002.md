# ADR-002 — Order correlation and aggregation strategy

**Status:** accepted

**Date:** 2026-10-04

## Context

The router splits one order into independent item messages, so the original order can no longer be represented by one message travelling through the system. The aggregator also has to handle multiple orders concurrently, delayed worker results, and RabbitMQ redeliveries.

The main decisions were how to preserve order correlation, when an order should become partial, what information a partial result should contain, and how to prevent duplicate worker results from being counted twice.

## Decision

The router uses `orderId` as the correlation identifier. Each item message contains `orderId`, `correlationId`, `itemIndex`, and `totalItems`. The router sets `correlationId` to the original `orderId`, so the aggregator can group results from different worker queues back into the correct order.

The aggregator stores active orders in an in-memory `in_flight` dictionary protected by a `threading.Lock`. Each order stores its expected item count, results keyed by `itemIndex`, and the time of its most recent result.

I chose an idle timeout of **5 seconds**. The timeout resets whenever a new result for an order is received. A background sweep runs every second and marks an order partial when it has been idle for more than five seconds. An idle timeout is preferable to a fixed deadline because an order with many items may legitimately take longer while results continue arriving.

A complete result is produced when every expected item index has been received. A partial result contains the results that did arrive, `receivedItems`, `totalItems`, and a `missingItemIndexes` list so the consumer can identify exactly which items are missing.

Results are stored by `itemIndex`. If RabbitMQ redelivers the same item result, the existing index is already present and the duplicate is ignored rather than counted again.

## Alternatives considered

A fixed deadline from the beginning of an order was considered instead of an idle timeout. I rejected it because a large order or a slow worker could still be making useful progress when the fixed deadline expired. Resetting the timeout on activity makes the partial result decision depend on actual inactivity.

A simple list of results was also considered. I rejected it because duplicate results would increase the count incorrectly. Using `itemIndex` as the dictionary key makes deduplication direct and also keeps results associated with their original item.

For aggregation state, an external store such as Redis would be more resilient, but I chose an in-memory dictionary for this assignment because the service is small and the required deployment has one aggregator instance.

## Consequences

The design keeps concurrent orders separated by `orderId`, provides useful partial results, and handles duplicate deliveries without double-counting. The five-second idle timeout also allows progress on large orders instead of imposing one fixed deadline.

The main cost is that aggregation state is held only in memory. If the aggregator container restarts before an order completes, its partial state is lost and the order cannot be reconstructed from that state. The in-memory approach would also become harder to scale to multiple aggregator instances; a shared store or coordinated consumer design would be needed for higher traffic or multiple replicas.

# ADR-006 — Use Temporal for durable checkout orchestration

**Status:** accepted  
**Date:** 2026-11-05

## Context

PA6 implemented checkout as a manual saga inside the Express `/checkout` handler in `pa6/orchestrator/src/server.ts`. It called payment authorization, inventory reservation, shipment creation, and notification in sequence. The `callStep()` function handled HTTP requests, timeouts, error classification, and trace entries. The handler tracked completed work using `paymentDone` and `inventoryDone`, then performed compensating calls when a later step failed.

The main weakness was crash recovery. PA6 persisted an idempotency record with state `in_progress` before starting downstream calls, but persisted the final saga result only after the operation finished. If the orchestrator process stopped during shipping, the JSON store could retain `in_progress` even though payment and inventory had already succeeded. A repeated request with the same key would then receive `409 idempotency_conflict`, without a running process available to finish the saga. This is a risk visible in the implementation, rather than a separately verified PA6 crash-test result.

PA7 needed to preserve the same business sequence and compensation behavior while allowing an interrupted worker to resume without restarting the entire checkout.

## Decision

Use Temporal to execute checkout as a durable workflow. The workflow is defined in `pa7/worker/src/workflows/checkout.ts`, while HTTP calls to the four mock services are implemented as activities in `pa7/worker/src/activities/index.ts`.

The workflow executes payment, inventory, shipping, and notification sequentially. It records successful steps and, on failure, releases inventory and refunds payment in reverse order when those operations were completed. The activity proxy uses a `2500 ms` start-to-close timeout and a retry policy of three maximum attempts, an initial interval of `200 ms`, and a backoff coefficient of `2`.

Activities distinguish permanent failures from retryable ones. HTTP 4xx responses are raised as non-retryable application failures, so a declined payment or refused reservation is not repeatedly attempted. Transient failures and timeouts may be retried within the configured limit. The workflow itself contains orchestration decisions; external HTTP requests stay in activities so that Temporal can record and replay workflow execution deterministically.

The API remains responsible for request validation, idempotency-key behavior, and the required audit representation. Temporal is responsible for durable execution and recovery of the saga.

## Alternatives considered

The main alternative was to keep the PA6 Express orchestrator and implement a recovery mechanism. That would require storing each completed step durably, detecting abandoned `in_progress` records after a restart, deciding whether a downstream operation had already succeeded, resuming from the correct step, and ensuring compensation was not duplicated. It could work, but it would mean implementing and maintaining a small workflow engine ourselves.

Another alternative was to retry every downstream error. We rejected this because a permanent business refusal, such as an HTTP 4xx payment decline, should not be treated like a network timeout. Retrying it wastes calls and may produce confusing audit records.

Temporal was chosen because durable workflow history, replay, activity scheduling, and retry management are built into the platform rather than implemented as application-specific recovery logic.

## Consequences

Worker interruption is easier to recover from. In the PA7 public crash test, the worker resumes and the payment is not taken twice. The workflow also has an explicit retry policy, and the public shipping-timeout test verifies three attempts followed by compensation.

However, Temporal provides **at-least-once activity execution**, not exactly-once execution of external side effects. A worker may complete an HTTP call and crash before Temporal records the activity completion. Temporal can then run that activity again. The shipping crash scenario demonstrates why downstream services must tolerate repeated requests. If payment authorization were repeated, the payment service would need its own idempotency protection to prevent a duplicate charge. Temporal alone cannot guarantee that.

The system is also more operationally complex. PA7 must run and monitor a Temporal service and worker alongside the API and mock services. Workflow histories and task queues become additional operational concerns. Deploying a changed workflow while older executions are still running requires care because replay must remain compatible with the recorded history; versioning or worker deployment strategies may be needed.

We accept these infrastructure and maintenance costs in exchange for durable recovery and a clearer separation between business orchestration and unreliable external operations.

## What the engine took over

- **Execution progress and crash recovery:** In PA6, the `/checkout` handler ran the `for (const step of steps)` loop in one Express request, with no durable per-step resume mechanism. In PA7, Temporal records workflow history and replays the workflow when a worker restarts, allowing it to continue from recorded progress.
- **Activity retries:** PA6's `callStep()` made a single Axios request and returned a failure or timeout result; there was no general retry scheduler. In PA7, Temporal applies the activity retry policy of three maximum attempts with exponential backoff, while non-retryable 4xx failures stop immediately.
- **Activity timeout management:** PA6 configured Axios with `requestTimeoutMs` and manually recognized `ECONNABORTED` and `ETIMEDOUT` inside `callStep()`. PA7 declares a `startToCloseTimeout` for activities, and the workflow can handle Temporal timeout failures.
- **Durable orchestration state:** PA6 manually wrote `in_progress` and final results into `idempotency-store.json` and `saga-store.json`, but those writes did not capture each intermediate activity completion for recovery. PA7 uses Temporal's persisted execution history for workflow progress. The API still maintains its own idempotency and audit responsibilities.
- **Rescheduling after worker failure:** PA6 depended on the Express process staying alive until the checkout request completed. PA7 allows Temporal to schedule outstanding work for a restarted worker instead of relying on the original process and call stack.

**Self-assessment:** The implemented workflow covers the four checkout activities, retry classification, compensation, idempotency behavior, audit mirroring, and worker recovery exercised by the public tests. The main remaining production concerns are downstream idempotency, Temporal operations, workflow versioning, and stronger monitoring. AI assistance was used to help implement and debug the assignment and draft this ADR; the behavior was checked against the local public tests.
